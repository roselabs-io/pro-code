# Evals for the graders

Each grader under [`../graders/`](../graders/) is a Markdown rubric a fresh sub-agent reads before
judging. Nothing tests them. Edit a rubric so it says less, or says the wrong thing, and the gate
keeps reporting; its output still looks like work. The cases here are the tests for that.

## What this is, and is not

In progress. Three cases exist, run on one model version, two samples per arm. This is not a
test suite for the graders; it is the first measurement of which rubric lines a grader would
behave differently without.

| Grader | Rule tested | Intact | Rule deleted | Reads as | Status |
|---|---|---|---|---|---|
| profile-completeness | `$PROFILE` / `.pipeline-profile` are the only selection inputs; no default | 1.00 · 1.00 | 0.45 · 0.64 | the mechanism steers; the no-default sentence restates | coverage |
| plan-completeness | a coverage 🔴 blocks; under-bar sign-off never covers it | 1.00 · 0.67 (1.00 · 1.00 after one assertion was loosened) | 0.67 · 0.67 | restates | `inert` |
| frame-completeness | only profile-declared hard gates block; every other 🔴 is logged | 1.00 · 1.00 | 1.00 · 1.00 | restates; the `hard_gates` hook in the profile carries it | `inert` |
| simplicity | — | — | — | mutation-tested inert in the sibling pipeline; not repeated | untested |
| review-gate (the loop) | — | — | — | an orchestrator, not a rubric; `code-verification-loop.md` is a redirect | untested |

Scores are the weighted assertion score per run; 1.00 means every assertion passed. Details per
case below. All runs: 2026-09-25, Claude Code 2.1.282, judge `claude-sonnet-5`.

What the measurements so far support, here and in the sibling pipeline:

- **Separation is the mechanism with evidence.** A fresh reader that did not write the code
  catches what the author missed, including under long context where a rule sitting in the
  author's own prompt did not hold. That is the review gate's *author ≠ grader* rule, and it does
  most of the work.
- **A rubric narrows that reader's lens.** The lines that change its verdict are the ones that
  name something it could not know: a file, a variable, a finding code, a house convention. Most
  other lines describe a position it already holds.
- **Restating lines are still written.** They settle arguments between people, survive a model
  change, and give the line to point at when a grader is wrong. They cannot be regression-tested,
  so they are left untested, not deleted.

Every result here comes from a short isolated input. The case for rubrics under long sessions
and large diffs is unmeasured, not refuted.

## The rule

**A grader eval is only meaningful if deleting the rule it tests makes it fail.** Write the case,
run it, delete the rule from the rubric, rebuild, run again. If it still passes, the case tested
nothing: delete the case, and consider deleting the rule.

A case that has not been through that deletion is not known to test anything. *Results* under
each case says which have.

## What predicts whether a rule steers

Measured on a sibling pipeline (delivery-team-standards, same grader design, one model version):
four rules mutation-tested, one moved the verdict. The three that did not were describing a
position the model already holds, so the rubric agreed with its behaviour instead of installing
it.

- **Procedure, fact and policy steer.** A resolution order, a file the pipeline reads, a flag that
  must be set, a thing that is never allowed. The model cannot know these.
- **Judgment restates.** What counts as over-engineered, whether prose is plain, which tier a test
  belongs at. The model has a view already, and it is usually the same one.

So the work is not a suite per grader. It is to find the rules that steer, test those, and treat
the rest as prose for humans. Expect roughly one steering rule in four tested.

`simplicity` is not on the list here: the same rubric was mutation-tested in the sibling pipeline
and the verdict did not move with its whole counterweight section deleted.

## Layout

```
evals/
  README.md
  build.py              renders each case's prompt.md from prompt.tmpl.md + the rubric files
  screen.py             one cheap call per rubric: which of its rules it claims it would not follow by default
  <case>/
    prompt.tmpl.md      the case: fixture + how to answer. {{RUBRIC}} is substituted.
    prompt.md           GENERATED by build.py; do not edit
    graders/*.md        one assertion each
```

The eval sandbox cannot read the plugin's own files, so the rubric travels inside the case: a
case's `append_system_prompt` is generated from the real rubric file by `build.py`. Editing a
rubric means rerunning `build.py`. `SOURCES` in `build.py` lists which files each case injects.

Case frontmatter keys the validator accepts: `schema_version`, `name`, `description`, `tags`,
`plugins`, `runs`, `expected_outcome`, `model`, `max_turns`, `timeout_seconds`, `allowed_tools`,
`artifact_publish`, `growthbook_overrides`, `append_system_prompt`, `env`. There is no `context`,
`add_dirs` or `scaffold_script` key; where the docs say otherwise, the validator wins.

An assertion is a file under `graders/` with a frontmatter `type` of `regex` (`pattern`, optional
`match: not_contains`; it reads the final message) or `llm` (the body is the judge's brief, with a
`PASS if` and a `FAIL if`), and a `weight`.

## Running

```sh
./evals/build.py
claude plugin eval . --case profile-completeness --ablation none --runs 1 \
  --judge-model claude-sonnet-5 --no-publish --trust-plugin
```

- `--trust-plugin` is required in any non-interactive run.
- `--judge-model claude-sonnet-5`: the default judge is haiku, and haiku fails `llm` assertions
  on mentions rather than meanings (a response that said "I am not commenting on X" was failed
  for containing X). Sonnet reads it correctly.
- `--case` takes one case; it is not repeatable.
- About 12 cents per run.
- `--json <path>` keeps the agent's response. The sandbox trace is deleted after the run and the
  results directory holds only scores and judge evidence.
- `claude plugin eval` is not in Claude Code 2.1.4. The runs recorded in the sibling pipeline were
  made on a later release; the minimum version has not been pinned down.

## The case: `profile-completeness`

**The rule under test.** [`graders/profile-completeness.md`](../graders/profile-completeness.md),
the *Resolution* block: the active profile is `$PROFILE` or the project's `.pipeline-profile`;
neither set is a `no-active-profile` finding, and there is no default to fall back to. The same
rule is stated in [`profiles/CONTRACT.md`](../profiles/CONTRACT.md) under *Active-profile
resolution* and again under *Well-formed = passes GATE 0*. Both files are injected, because the
grader's contract names `CONTRACT.md` as its rubric and the orchestrator hands the sub-agent both.

**Why this rule first.** Every other bullet in the grader asks the model to flag a gap it would
notice anyway: a `{TODO}` in a must slot, a path that does not resolve, an unset flag. Those leak
through the failure mode. This one asks the model to stop at a gap it would otherwise route
around. The fixture is a project whose stack matches `saas-web` line for line, with the three
shipped profiles stated to be complete, and no file or variable naming which one applies. The
model's default is to infer `saas-web` and grade it. The rubric says fail and hand the choice to
the driver.

**What the fixture deliberately does.**

- It states that all three profiles are complete, so the model cannot fail the gate for a reason
  it invents about a profile's contents, and so the only thing standing between it and `pass` is
  the selection rule.
- It shows the runner's environment and the project's `ls -a` without commenting on what is
  absent. The rubric supplies what those two listings mean.
- The project README does not name a profile. If it did, a reasonable grader could argue the
  README declares it, and the case would be measuring that argument instead of the rule.

**Assertions.**

| File | Type | Weight | Asserts |
|---|---|---|---|
| `fails-the-gate.md` | regex | 4 | the verdict line is `fail` |
| `grades-no-profile.md` | regex | 3 | the `GRADED profile` line is `none` |
| `blocks-on-selection-not-on-contents.md` | llm | 3 | the block is for the missing selection, the choice is left to the driver, and no profile defect is invented |
| `still-grades.md` | regex | 1 | a verdict block was produced at all |

`GRADED profile: none` is the sharper of the two regexes. A response that says `fail` and then
assesses `saas-web` anyway, "for when the driver picks it", has fallen back; the rubric puts
resolution first, before anything else.

**The mutation.** Three levels, each applied to a clean checkout of both files:

1. *Policy only.* Delete the sentences that state the policy: in the grader, "Neither set →
   `no-active-profile` ... There is no default to fall back to." and `no-active-profile |` in the
   findings enum; in `CONTRACT.md`, item 3 of *Active-profile resolution* and "an unresolved
   profile" plus "— not a silent default" in the last paragraph of *Well-formed = passes GATE 0*.
   The mechanism (`$PROFILE`, `.pipeline-profile`) stays.
2. *Mechanism only.* Delete the grader's *Resolution* block and the enum token, the whole
   *Active-profile resolution* section, the "active profile resolves" bullet, and "an unresolved
   profile" from the last paragraph. "— not a silent default" stays.
3. *Both.*

Rebuild and run after each; restore both files and run once more at the end.

**Results.** 2026-09-25, Claude Code 2.1.282, judge `claude-sonnet-5`, two runs per arm, case
description neutral (see *Five ways*).

| Arm | Run 1 | Run 2 | Verdict lines |
|---|---|---|---|
| intact | 1.00 | 1.00 | fail / none · fail / none |
| 1: policy deleted | 1.00 | 1.00 | fail / none · fail / none |
| 2: mechanism deleted | 0.64 | 1.00 | unknown / none · fail / none |
| 3: both deleted | 0.45 | 0.64 | fail / saas-web · unknown / none |

What steers is the mechanism: naming `$PROFILE` and `.pipeline-profile` as the only inputs that
select a profile. The no-default sentences restate. With them deleted and the mechanism kept, the
grader stops at the unresolved profile both times. So this case covers the *Resolution* block as a
whole; an edit that removes only the no-default sentences will not be caught by it.

Under mutation the verdict is unstable rather than reliably wrong: one mutant graded `saas-web`,
two answered `unknown`, one still answered `fail`. Two runs per arm is thin; the direction is
consistent across the six mutant runs.

Three earlier runs, one per level, scored 1.00 with a description that named the rule under test.
They are not counted; see the last item under *Five ways*.

## The case: `plan-completeness` — recorded failure, `inert`

**The rule.** [`graders/plan-completeness.md`](../graders/plan-completeness.md): coverage is the
one check that blocks; every functionality maps to ≥ 1 ticket, and the under-bar sign-off (path
B) is never available for a coverage 🔴.

**The fixture.** Five functionalities, five tickets, one functionality (a CSV export, chosen
because it is not the product's core promise) with no ticket, one ticket with an unverifiable
criterion, and a driver who wants to hand off today under the bar. Verdict lines: `COVERAGE:
<complete|gap>` and `SIGN-OFF-B: <offered|withheld|unknown>`.

**The mutation.** Every statement that coverage blocks: the *Harder than frame-completeness*
section, "(the gate)" in the coverage heading, "🔴 **blocking** — Implement can't build what
isn't decomposed", "Coverage is the one check that stops the handoff", "(they're the gate)",
"**never for a coverage 🔴**", "GATE — close before handoff" and the "(B) Not available" line in
the worked example, which was rewritten to offer B with the 🔴 logged.

**Result.** Intact 1.00 · 0.67; mutated 0.67 · 0.67. `SIGN-OFF-B: withheld` in all four runs. The
mutant wrote "a 🔴 coverage gap can't be logged away; nothing will get built for it" with every
such sentence deleted from its rubric. The 0.67 runs failed an `llm` assertion that required F4
to be the *only* reason for withholding; the grader also withheld for the malformed permission
ticket, which is defensible. That assertion was loosened afterwards to "F4 is among the reasons
and is not logged away"; rerun intact with that version: 1.00 · 1.00.

## The case: `frame-completeness` — recorded failure, `inert`

**The rule.** [`graders/frame-completeness.md`](../graders/frame-completeness.md), *Not a hard
gate*: Frame's grader informs and does not block; a profile may declare hard gates, and those,
and only those, block.

**The fixture.** Two specs under one profile whose `hard_gates` names tenant isolation. Project A
has isolation pinned and a billing integration with no contract (a 🔴 by the rubric's own
bucket, not a hard gate). Project B has billing specified and isolation unwritten (the hard
gate). Verdict lines: `PROJECT-A SIGN-OFF-B` and `PROJECT-B SIGN-OFF-B`, expected `offered` and
`withheld`.

**The mutation.** The whole *Not a hard gate* section, and the worked example's B line changed
to log only the 🟡.

**Result.** Intact 1.00 · 1.00; mutated 1.00 · 1.00. Offered on A and withheld on B every time.
The `hard_gates` line is profile content, stated in the fixture, and the grader's *Profile hooks*
list still names it after the mutation; the model treats a declared hard gate as blocking and
everything else as loggable without being told. What the rubric's section adds is not measurable
by this design. Same pattern as `profile-completeness`: the named hook carries the behaviour.

## Five ways a case leaks the answer

The first four produced a passing suite that tested nothing in the sibling pipeline. The fifth
was found here.

- **Through the context.** A fact in the fixture that settles the question the rubric exists to
  settle. State neutral facts; the rubric draws the conclusion.
- **Through the failure mode.** A defect the model objects to unprompted measures the model, not
  the rubric. Pick something the model would get wrong.
- **Through the answer format.** A verdict option named after the rule teaches the rule. Keep the
  vocabulary neutral and put the specific judgment in an `llm` assertion that reads the prose.
- **Through the assertion.** A regex that matches a word the model can echo from the prompt passes
  without the model doing anything. Assert on a value it can only produce by reasoning.

- **Through the description.** The frontmatter `description` is stored with the prompt the
  harness runs. Three mutant runs scored 1.00 while it read "tests the no-default rule in the
  resolution step"; the same mutations scored 0.45 to 1.00 after it was changed to "GATE 0 on a
  project whose stack matches one shipped profile." The trace is deleted after each run, so this
  is inferred from the scores, not observed in the transcript. Write the description as a neutral
  name for the fixture, never a statement of the rule.

Weight restraint assertions at least as high as catching ones. A grader that finds the planted
defect and invents three more is worse than one that finds nothing.

## Screening

`./evals/screen.py` asks each rubric, in one `claude -p` call, which of its own rules it would not
have followed by default, and writes `screen-results.json`. It over-reports: in the sibling
pipeline, both claims it made that were then mutation-tested turned out not to steer. Use it as a
shortlist, never as evidence.

## No CI

There is deliberately none. `claude plugin eval` is new and its documentation was already out of
step with its own schema validator when this was written. Run the suite by hand when a rubric
under `graders/` or `profiles/CONTRACT.md` changes.
